## Інструкції для агента

Усі правила — у [CLAUDE.md](CLAUDE.md). Головні з них:
- спершу дослідити реальну поведінку сайту й API (локатори, тексти помилок, статус-коди) і звірити з документацією;
- неправильна поведінка — це баг: перевірка через `knownBug()` (правильна поведінка + спостережуваний баг) і
  баг-репорт у README; `test.fail()` заборонений, бо «зеленить» будь-яке падіння;
- шари: page objects у `src/pages`, дані в `src/data`, хелпери в `src/utils`, середовище в `config/env.ts`;
  у тестах — лише перевірки, без жодного сирого локатора;
- перевіряти значення (точні тексти, повні списки, суми); тест має вміти впасти на реальній регресії;
- без `waitForTimeout`, без збільшення таймаутів і ретраїв, щоб сховати падіння.

## Етапи роботи

1. **Дослідження без коду.** Короткими скриптами зібрати реальну поведінку: data-test атрибути, точні тексти
   помилок, податок, порожній кошик; для API — статус-коди на успішний флоу і на некоректні запити.
2. **UI- і API-тести**, баг-репорти, GitHub Actions.
3. **Перебудова за шарами:** pages / tests / data / utils / config + `.env`; компонент шапки, сторінка товару,
   вхід через cookie сесії; Arrange → Act → Assert.
4. **Бонус:** конвеєр «тест-кейс текстом → Playwright-тест» через Claude Code у headless-режимі.
5. **Незалежне рев'ю** і виправлення за ним (див. нижче).
6. **Allure** (звіт у CI + GitHub Pages з історією) і **порівняння скріншотів** (еталони для Windows і Linux).

## Де агент помилився і як це помітили

1. **`test.fail()` ховав будь-яке падіння.** Відомі баги спершу були оформлені як тести з `test.fail()`. Такий
   тест «зеленіє» на будь-якій помилці — 503 від пісочниці, зламаному локаторі, друкарській помилці. Помітив
   незалежний рев'юер. Замінено на `knownBug()` (правильна поведінка + підтвердження саме цього бага) і перевірено
   експериментом: з неправильною адресою API всі 6 API-тестів на баги тепер червоні, а сценарій «баг виправили»
   теж дає червоний тест із поясненням.
2. **Тест на баг «падав» не через баг.** Під час перебудови агент додав у `InventoryPage` метод `cartButton()`
   через `getByRole('button')` у картці товару. Картка містить кілька таких елементів, і BUG-UI-3 почав падати на
   strict mode violation, а не на перевірці бага — набір лишався зеленим, хоча тест нічого не доводив. Помітили,
   коли перевіряли причину падіння кожного тесту на баг; локатор виправлено, тепер видно «Expected: Add to cart,
   Received: Remove». (Саме цей випадок і показав, що підхід із пункту 1 треба міняти.)
3. **Тест сортування A→Z не міг упасти.** Агент вибирав «A to Z» на свіжій сторінці, але це і є порядок за
   замовчуванням: зламане сортування тест би не помітив. Помітив незалежний рев'юер. Тепер кожне сортування
   спершу ставить протилежний порядок і перевіряє, що список справді інший, і лише потім перемикає.
4. **Конвеєр бонусу рахував пропущений тест пройденим.** Для кейсу, де бракувало методу в page objects, модель
   правильно згенерувала тест зі `skip`, але перша версія `bonus/generate.mjs` дивилась лише на код виходу
   Playwright (0) і написала «PASSED». Помітили, читаючи згенерований файл і `run.log` («1 skipped»). Поточна
   версія вимагає реально пройдений тест, перевіряє типи й сирі селектори і не перезаписує переглянуті тести.
   Запис першої версії лишено як доказ: `bonus/examples/04-open-product-by-image/attempt-1/`.
5. **Перевірка «навиворіт».** Агент написав `expect([200, 204]).toContain(status)`: при падінні звіт показував
   «Expected: 201, Received: [200, 204]» — тобто навпаки, і читач плутався, що є очікуваним. Помітили, коли
   читали причину падіння. Переписано так, щоб звіт казав, що очікувалось і що прийшло.

Дрібніші випадки, виправлені по ходу: проєкт спершу створено не в тій папці (помітив я); застаріла опція
`moduleResolution: "node"` (впала перевірка типів); тест повного циклу API не прибирав бронювання при падінні
посередині; DELETE → 201 спершу записано як баг, хоча так описано в документації API (рев'юер, перевірено в
документації — тепер це API-NOTE-1).
