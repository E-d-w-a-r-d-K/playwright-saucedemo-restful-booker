## Інструкції для агента

Усі правила — у [CLAUDE.md](CLAUDE.md). Головні з них:
- спершу дослідити реальну поведінку сайту й API (локатори, тексти помилок, статус-коди) і лише потім писати тести;
- неправильна поведінка — це баг: тест пишеться на правильну поведінку з `test.fail()` + баг-репорт у README,
  а не «закріплюється» як очікувана;
- перевіряти значення (точні тексти, повні списки, суми), а не лише наявність елемента;
- для кожного `test.fail` один раз зняти позначку й переконатися, що тест падає саме на баг, а не на зламаному локаторі;
- без `waitForTimeout`, без збільшення таймаутів і ретраїв, щоб сховати падіння.

## Де агент помилився і як це помітили

1. **Створив проєкт не в тій папці.** Агент розмістив репозиторій у робочій папці поруч з іншим проєктом.
   Помітив я одразу після першої команди, зупинив і попросив перенести в окрему папку — перенесено, git налаштовано
   на мій акаунт.
2. **Застаріла опція TypeScript.** У `tsconfig.json` агент поставив `"moduleResolution": "node"`. Поточна версія
   TypeScript цю опцію вже не приймає: `npm run typecheck` впав з помилкою TS5108. Замінено на
   `"moduleResolution": "bundler"`; після цього перевірка типів проходить.
3. **Перевірка «навиворіт» у тесті на баг.** У BUG-API-3 агент написав `expect([200, 204]).toContain(status)`.
   Тест падав правильно, але звіт показував «Expected: 201, Received: [200, 204]» — тобто навпаки. Помітили,
   коли зняли `test.fail` і читали причину падіння. Переписано так, що звіт каже «DELETE should answer 200 or 204, got 201».
4. **Не той атрибут для локаторів.** Агент почав писати page objects через `getByTestId`, не врахувавши, що
   Playwright за замовчуванням шукає `data-testid`, а saucedemo використовує `data-test`. Помічено на рев'ю коду до
   першого запуску; додано `testIdAttribute: 'data-test'` у конфіг проєкту `ui`.
5. **Зайвий дубль тесту.** У файл із відомими багами агент додав ще й «позитивний» тест заповненої форми чекауту,
   який повністю дублював основний тест чекауту. Помічено на рев'ю, тест видалено.
