# QA test task: saucedemo UI + restful-booker API

[![tests](https://github.com/E-d-w-a-r-d-K/playwright-saucedemo-restful-booker/actions/workflows/tests.yml/badge.svg)](https://github.com/E-d-w-a-r-d-K/playwright-saucedemo-restful-booker/actions/workflows/tests.yml)

Автотести на **Playwright + TypeScript**:
- UI — https://www.saucedemo.com (користувач `standard_user`);
- візуальні порівняння сторінок (скріншоти проти затверджених еталонів);
- API — https://restful-booker.herokuapp.com.

Тести запускаються в GitHub Actions на кожен push. **Allure-звіт** останнього прогону `main` публікується на
https://e-d-w-a-r-d-k.github.io/playwright-saucedemo-restful-booker/ і зберігається як артефакт кожного прогону.

Як агент допомагав і де помилявся — [AI_WORKLOG.md](AI_WORKLOG.md), правила для агента — [CLAUDE.md](CLAUDE.md).
Бонус (тест-кейс текстом → Playwright-тест) — [bonus/README.md](bonus/README.md).

## Як запустити

Потрібен Node.js 20.12+ (CI — Node 22).

```bash
npm ci
npx playwright install chromium
npm test                    # усі тести: ui + visual + api
npm run test:ui             # лише UI
npm run test:visual         # лише порівняння скріншотів
npm run test:api            # лише API
npm run typecheck           # перевірка типів
npm run report              # HTML-звіт Playwright
npm run allure:generate     # Allure-звіт з результатів останнього прогону
npm run allure:open         # відкрити Allure-звіт
```

У CI (вкладка **Actions** → запуск) є артефакти:
- **allure-report** — Allure-звіт;
- **playwright-report** — HTML-звіт Playwright;
- **test-results** — JUnit XML, а для тестів, що впали, ще трейси, скріншоти й картинки різниці скріншотів.

### Що видно в Allure-звіті

- **Кроки відтворення.** Кожна дія page object і кожен запит API — окремий крок із даними: «Add "Sauce Labs Backpack"
  to the cart», «Fill in the customer form (…) and continue», «POST /booking». Кожна перевірка має підпис: «the cart
  badge shows 2», «PUT with a forged token answers 403». Тест читається як баг-репорт: що зробили і що перевірили.
- **Крок, на якому впало.** Він червоний, у ньому рядок коду, Expected / Received; усі кроки до нього зелені.
  До UI-тесту, що впав, прикладені скріншот, контекст сторінки і Playwright trace (відкривається просто у звіті).
- **API:** у кожному запиті прикладені тіло запиту (пароль замаскований) і відповідь зі статусом.
- **Групування:** вкладка Behaviors — епік (UI / скріншоти / API) → розділ (Login, Cart, Checkout…);
  серйозність — `critical` для головного сценарію розділу, для відомих багів — з баг-репорту.
- **Відомі баги** мають посилання на свій баг-репорт у цьому README; крок «correct behaviour» показує, що саме
  мало б бути, а «observed» — що підтверджено.
- **Історія** прогонів (вкладка History) — зберігається між запусками CI.

### Інше середовище

Адреси й облікові дані читаються з [config/env.ts](config/env.ts): змінні оточення або локальний `.env`
(зразок — [.env.example](.env.example)). Без `.env` тести йдуть на публічні демо-сайти.

```bash
cp .env.example .env    # змінити UI_BASE_URL / API_BASE_URL на dev, staging або локальну копію
npm test
```

```
src/

    api.ts                client, token, cleanup (видаляє створені бронювання навіть після падіння)
  data/                   тестові дані окремо від коду: користувачі, каталог, покупець, тексти,

    session.ts            швидкий вхід через cookie для тестів, яким форма не потрібна
    knownBug.ts           перевірка відомого бага, яка не ховає сторонніх падінь (див. нижче)

    login  catalog  cart  checkout  known-bugs
    generated/            тести з бонус-конвеєра, переглянуті вручну
  visual/
    pages.visual.spec.ts  порівняння скріншотів
    __screenshots__/      затверджені еталони: win32/ для локального запуску, linux/ для CI
    screenshot.css        стилі на час знімка (ховає рік у футері)
  api/
    booking  known-bugs
bonus/                    конвеєр «тест-кейс текстом → Playwright-тест» і приклади
.github/workflows/
  tests.yml               тести, Allure-звіт, публікація на GitHub Pages
  update-screenshots.yml  оновлення Linux-еталонів скріншотів (запуск вручну)
```

Правила шарів:
- у `tests/` немає `getByTestId`, `locator`, CSS чи XPath — тільки методи й локатори page objects;
- дані (облікові записи, каталог, тексти помилок, маршрути) лежать у `src/data`, а не в тестах;
- форму логіну перевіряє `login.spec.ts`; решта UI-тестів входить через cookie сесії — швидше й не залежить від форми;
- UI, visual і API — окремі проєкти Playwright зі своїми фікстурами; повтор після падіння (1 раз, лише в CI)
  дозволений тільки API-проєкту через публічну пісочницю, і такий тест позначається як `flaky`, а не ховається.

## Що покрито

Усього **46 тестів**: UI 21 + 3 відомі баги + 5 згенерованих, visual 5 + 1 відомий баг, API 5 + 6 відомих багів.
Цифри в завданні («5–7 основних, 2–3 негативні») свідомо перевищені: сортування перевірене для всіх 4 варіантів,
а кожне обов'язкове поле чекауту — окремим тестом.

**UI**

| Сценарій | Що саме перевіряється |
|---|---|
| Логін | вхід через форму → Products і всі 6 товарів; вихід через меню закриває доступ до `/inventory.html` |
| Каталог | повний список назв і цін; сторінка товару — та сама назва, ціна й опис, що й картка |
| Сортування | A→Z і Z→A: **увесь** список після перемикання з протилежного порядку (A→Z — порядок за замовчуванням, тож на свіжій сторінці він нічого б не довів); за ціною ↑ і ↓: уся послідовність цін і набір товарів (два товари по $15.99, їхній порядок вимогами не визначений) |
| Кошик | 2 товари з цінами й лічильник 2; видалення одного; видалення **останнього** — кошик порожній, лічильника немає; кошик зберігається після перезавантаження |
| Чекаут | Backpack + Bolt T-Shirt: суми з реальної сторінки ($45.98 / $3.68 / $49.66) і правило «сума цін, 8% податку, разом»; замовлення завершене, кошик порожній |
| Негативні й граничні | неправильний пароль; логін чутливий до регістру (`Standard_User`); `locked_out_user`; порожня форма; `/inventory.html` без входу; порожні ім'я / прізвище / індекс у чекауті — кожне поле окремо, з точним текстом помилки |

**Visual** — затверджені еталони сторінок: логін, каталог (повна сторінка), сторінка товару, кошик із 2 товарами,
огляд замовлення. Допуск — до 100 пікселів (еталони окремі для кожної ОС, тож справжня сторінка відрізняється лише кількома
пікселями згладжування; відсотковий допуск на всю сторінку пропустив би цілу зламану картинку товару), анімації вимкнені, рік у футері прихований (інакше
1 січня падали б усі еталони). Що система справді ловить зміни, доводить **BUG-VIS-1**: каталог `visual_user`
порівнюється з еталоном `standard_user` і має не збігтися — в Allure видно еталон, фактичний знімок і різницю.

**API**

| Сценарій | Що саме перевіряється |
|---|---|
| Флоу | auth → токен; create → id і тіло дорівнює надісланому; get → те саме; update з токеном → нові дані в GET; delete → 201 (так задокументовано, див. API-NOTE-1); get → 404 |
| Негативні | update без токена → 403, бронювання не змінилось; delete без токена → 403, бронювання на місці; update і delete з підробленим токеном → 403; неіснуючий id → 404 |

Кожен тест незалежний: свій вхід, свої дані. API-тести створюють бронювання з унікальним прізвищем і
видаляють їх після себе навіть після падіння — пісочниця спільна для всіх, хто її тестує.

### Як перевіряються відомі баги

Не через `test.fail()`: той «зеленіє» на **будь-якому** падінні — на 503 від пісочниці, зламаному локаторі,
друкарській помилці. Натомість [src/utils/knownBug.ts](src/utils/knownBug.ts) робить дві перевірки:
1. **правильна поведінка** — поки баг є, вона має не виконатись;
2. **спостережувана поведінка бага** — має виконатись (наприклад, «статус 200 і тіло `{"reason":"Bad credentials"}`»).

Тест зелений, лише коли є **саме цей** баг. Якщо API недоступне чи змінився локатор — червоний. Якщо баг
виправили — теж червоний, із підказкою перенести перевірку в звичайні тести. Перевірено: з неправильною адресою
API всі 6 API-тестів на баги падають (з `test.fail()` вони були б зелені).

## Що свідомо не покрито

- **Інші користувачі saucedemo** (`problem_user`, `performance_glitch_user`, `error_user`) — завдання про `standard_user`; `visual_user` використано лише як доказ для порівняння скріншотів.
- **Інші браузери й мобільний вигляд** — лише Chromium, щоб CI був швидким.
- **Доступність і продуктивність.**
- **API:** `PATCH /booking/{id}`, фільтри `GET /booking?firstname=…`, `GET /ping`, авторизація через Basic Auth.
- **Сторінки всіх 6 товарів** — перевірена одна сторінка товару; решта мають ту саму розмітку.

<a id="BUG-UI-1"></a>

### BUG-UI-1. Замовлення оформлюється з порожнім кошиком
- **Серйозність:** critical — оформлюється замовлення без товарів.
- **Середовище:** saucedemo.com, `standard_user`, Chrome.
- **Кроки:** 1) увійти; 2) не додаючи товарів, відкрити кошик; 3) Checkout; 4) заповнити ім'я, прізвище, індекс → Continue; 5) Finish.
- **Очікувано:** з порожнім кошиком Checkout не відкриває оформлення.
- **Фактично:** відкривається підсумок «Item total: $0 / Tax: $0.00 / Total: $0.00», після Finish — «Thank you for your order!».

### BUG-API-1. Неправильні облікові дані → 200 OK

<a id="API-NOTE-1"></a>

### API-NOTE-1. DELETE відповідає 201 Created (задокументовано)
`DELETE /booking/{id}` повертає `201 Created`. Документація restful-booker прямо описує саме таку відповідь,
тож це не баг проти специфікації, а відхилення від семантики HTTP (очікувано `200` або `204`): низька
серйозність, питання до власників API. Тест флоу перевіряє `201` як задокументовану поведінку.
