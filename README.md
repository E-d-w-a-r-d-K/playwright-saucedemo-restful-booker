# QA test task: saucedemo UI + restful-booker API

[![tests](https://github.com/E-d-w-a-r-d-K/playwright-saucedemo-restful-booker/actions/workflows/tests.yml/badge.svg)](https://github.com/E-d-w-a-r-d-K/playwright-saucedemo-restful-booker/actions/workflows/tests.yml)

Автотести на **Playwright + TypeScript**:
- UI — https://www.saucedemo.com (користувач `standard_user`);
- візуальні порівняння сторінок (скріншоти проти затверджених еталонів);
- API — https://restful-booker.herokuapp.com.

Тести запускаються в GitHub Actions на кожен push. **Allure-звіт** останнього прогону `main` публікується на
https://e-d-w-a-r-d-k.github.io/playwright-saucedemo-restful-booker/ і зберігається як артефакт кожного прогону.

Як агент допомагав і де помилявся — [AI_WORKLOG.md](AI_WORKLOG.md), правила для агента — [CLAUDE.md](CLAUDE.md).
Бонус (тест-кейс текстом → Playwright-тест) — [bonus/README.md](bonus/README.md).

## Як запустити

Потрібен Node.js 20.12+ (CI — Node 22).

```bash
npm ci
npx playwright install chromium
npm test                    # усі тести: ui + visual + api
npm run test:ui             # лише UI
npm run test:visual         # лише порівняння скріншотів
npm run test:api            # лише API
npm run typecheck           # перевірка типів
npm run report              # HTML-звіт Playwright
npm run allure:generate     # Allure-звіт з результатів останнього прогону
npm run allure:open         # відкрити Allure-звіт
```

У CI (вкладка **Actions** → запуск) є артефакти:
- **allure-report** — Allure-звіт;
- **playwright-report** — HTML-звіт Playwright;
- **test-results** — JUnit XML, а для тестів, що впали, ще трейси, скріншоти й картинки різниці скріншотів.

### Що видно в Allure-звіті

- **Кроки відтворення.** Кожна дія page object і кожен запит API — окремий крок із даними: «Add "Sauce Labs Backpack"
  to the cart», «Fill in the customer form (…) and continue», «POST /booking». Кожна перевірка має підпис: «the cart
  badge shows 2», «PUT with a forged token answers 403». Тест читається як баг-репорт: що зробили і що перевірили.
- **Крок, на якому впало.** Він червоний, у ньому рядок коду, Expected / Received; усі кроки до нього зелені.
  До UI-тесту, що впав, прикладені скріншот, контекст сторінки і Playwright trace (відкривається просто у звіті).
- **API:** у кожному запиті прикладені тіло запиту (пароль замаскований) і відповідь зі статусом.
- **Групування:** вкладка Behaviors — епік (UI / скріншоти / API) → розділ (Login, Cart, Checkout…);
  серйозність — `critical` для головного сценарію розділу, для відомих багів — з баг-репорту.
- **Відомі баги** мають посилання на свій баг-репорт у цьому README; крок «correct behaviour» показує, що саме
  мало б бути, а «observed» — що підтверджено.
- **Історія** прогонів (вкладка History) — зберігається між запусками CI.

### Інше середовище

Адреси й облікові дані читаються з [config/env.ts](config/env.ts): змінні оточення або локальний `.env`
(зразок — [.env.example](.env.example)). Без `.env` тести йдуть на публічні демо-сайти.

```bash
cp .env.example .env    # змінити UI_BASE_URL / API_BASE_URL на dev, staging або локальну копію
npm test
```

Правила шарів:
- у `tests/` немає `getByTestId`, `locator`, CSS чи XPath — тільки методи й локатори page objects;
- дані (облікові записи, каталог, тексти помилок, маршрути) лежать у `src/data`, а не в тестах;
- форму логіну перевіряє `login.spec.ts`; решта UI-тестів входить через cookie сесії — швидше й не залежить від форми;
- UI, visual і API — окремі проєкти Playwright зі своїми фікстурами; повтор після падіння (1 раз, лише в CI)
  дозволений тільки API-проєкту через публічну пісочницю, і такий тест позначається як `flaky`, а не ховається.

## Що покрито

Усього **86 тестів**: UI 43 + 5 відомих багів + 6 згенерованих, visual 5 + 4 перевірки чутливості + 1 відомий баг,
API 12 + 10 відомих багів.
Цифри в завданні («5–7 основних, 2–3 негативні») свідомо перевищені: сортування перевірене для всіх 4 варіантів,
а кожне обов'язкове поле чекауту — окремим тестом.

**API**

| Сценарій | Що саме перевіряється |
|---|---|
| Флоу | auth → токен; create → id і тіло дорівнює надісланому; get → те саме; update з токеном → нові дані в GET; delete → 201 (так задокументовано, див. API-NOTE-1); get → 404 |
| Пошук | новий id є у списку всіх бронювань; пошук за ім'ям і прізвищем і лише за прізвищем повертає рівно це бронювання, з іншим ім'ям — нічого; фільтр за датою заїзду: день до — знаходить, день після — ні (межа «той самий день» і фільтр за виїздом — відомі баги BUG-API-7, BUG-API-8) |
| Часткове оновлення (PATCH) | з токеном змінює лише надіслані поля, решта як була (і в GET); без токена і з підробленим токеном → 403, нічого не змінилось |
| Health check | `GET /ping` → 201 Created (так задокументовано) |
| Негативні | update без токена → 403, бронювання не змінилось; delete без токена → 403, бронювання на місці; update і delete з підробленим токеном → 403; неіснуючий id → 404 |

Кожен тест незалежний: свій вхід, свої дані. API-тести створюють бронювання з унікальним прізвищем і
видаляють їх після себе навіть після падіння — пісочниця спільна для всіх, хто її тестує.

### Як перевіряються відомі баги

Не через `test.fail()`: той «зеленіє» на **будь-якому** падінні — на 503 від пісочниці, зламаному локаторі,
друкарській помилці. Натомість [src/utils/knownBug.ts](src/utils/knownBug.ts) робить дві перевірки:
1. **правильна поведінка** — поки баг є, вона має не виконатись;
2. **спостережувана поведінка бага** — має виконатись (наприклад, «статус 200 і тіло `{"reason":"Bad credentials"}`»).

Коли доказом є саме падіння правильної перевірки (скріншот), вона має впасти з очікуваної причини — різниця
пікселів, а не відсутній еталон чи таймаут.

Тест зелений, лише коли є **саме цей** баг. Якщо API недоступне чи змінився локатор — червоний. Якщо баг
виправили — теж червоний, із підказкою перенести перевірку в звичайні тести. Перевірено: з неправильною адресою
API всі 10 API-тестів на баги падають (з `test.fail()` вони були б зелені).

## Що свідомо не покрито

- **Інші користувачі saucedemo** (`problem_user`, `performance_glitch_user`, `error_user`) — завдання про `standard_user`; `visual_user` використано лише як доказ для порівняння скріншотів.
- **Інші браузери й мобільний вигляд** — лише Chromium, щоб CI був швидким.
- **Доступність і продуктивність.**
- **API:** авторизація через Basic Auth (альтернатива токену в cookie) і відповіді у форматах XML та URL-encoded — усі тести працюють із JSON.
- **Lazy Load до кінця:** список нескінченний (за кодом сайту — ті самі 22 картки по колу), тож перевіряються механізм підвантаження, перші 12 карток точно й наступна порція, а не «кінець».
- **PATCH окремих вкладених полів** (наприклад, лише `bookingdates.checkout`) — перевірено PATCH двох полів верхнього рівня.

### BUG-UI-1. Замовлення оформлюється з порожнім кошиком

<a id="BUG-UI-4"></a>

### BUG-UI-4. Слайдер перемикає товар, який користувач щойно вибрав
- **Серйозність:** minor — вибраний товар може зникнути з екрана за частку секунди. Опису того, як має поводитись
  слайдер, на сайті немає: це UX-дефект за загальноприйнятою поведінкою каруселі, варто підтвердити з власником продукту.
- **Середовище:** https://www.saucedemo.com, `standard_user`, Chromium (Playwright), 25.11.2026.
- **Кроки:** 1) меню → Dynamic Catalog → Slider; 2) дочекатися, поки слайдер майже перемкнеться сам (він
  перемикається кожні 2 с); 3) натиснути крапку будь-якого товару, крім останнього (у поточному порядку, наприклад, «Show Sauce Labs Backpack»).
- **Очікувано:** вибраний товар лишається на екрані повний інтервал (2 с), автопрокрутка відраховує час від вибору.
- **Фактично:** таймер автопрокрутки не скидається: якщо вибрати товар за 10 мс до чергового перемикання, через
  10 мс показується наступний (для Backpack — Fleece Jacket). У коді сайту інтервал створюється один раз і не
  перезапускається після кліку. Під час дослідження також помічено, що автопрокрутка не зупиняється при наведенні
  й не має кнопки паузи (тестом це не перевіряється).
- **Тест:** BUG-UI-4 (з керованим годинником; перед кожним кроком часу тест чекає, поки сторінка оновиться й зареєструє таймер).

<a id="BUG-API-1"></a>

### BUG-API-1. Неправильні облікові дані → 200 OK
- **Серйозність:** critical — клієнт, що дивиться лише на статус, вважатиме вхід успішним.
- **Середовище:** https://restful-booker.herokuapp.com, 25.11.2026.
- **Запит:** `POST /auth` з `{"username":"admin","password":"wrong"}`.
- **Очікувано:** `401 Unauthorized`.
- **Фактично:** `200 OK`, тіло `{"reason":"Bad credentials"}`. У документації API ця відповідь не описана.
- **Відтворення:**
  ```bash
  curl -i -X POST https://restful-booker.herokuapp.com/auth -H 'Content-Type: application/json' -d '{"username":"admin","password":"wrong"}'
  ```
- **Тест:** `tests/api/known-bugs.spec.ts` → BUG-API-1.

<a id="BUG-API-3"></a>

### BUG-API-3. Дії з бронюванням, якого немає → 405
- **Серйозність:** minor — неправильний код помилки.
- **Середовище:** https://restful-booker.herokuapp.com, 25.11.2026.
- **Кроки:** 1) видалити бронювання і повторити `DELETE /booking/{id}` з тим самим id і токеном; 2) `PUT` і
  `PATCH` на id, якого ніколи не було, з дійсним токеном.
- **Очікувано:** `404 Not Found`.
- **Фактично:** `405 Method Not Allowed`, тіло — текст `Method Not Allowed`, в усіх трьох випадках.
- **Відтворення:**
  ```bash
  curl -i -X DELETE https://restful-booker.herokuapp.com/booking/<id> -H 'Cookie: token=<token з POST /auth>'   # другий раз для того самого id
  curl -i -X PUT https://restful-booker.herokuapp.com/booking/2147483000 -H 'Content-Type: application/json' -H 'Cookie: token=<token>' -d '{"firstname":"X","lastname":"Y","totalprice":1,"depositpaid":true,"bookingdates":{"checkin":"2027-01-01","checkout":"2027-01-02"}}'
  curl -i -X PATCH https://restful-booker.herokuapp.com/booking/2147483000 -H 'Content-Type: application/json' -H 'Cookie: token=<token>' -d '{"firstname":"X"}'
  ```
- **Тест:** BUG-API-3 (три тести: повторне видалення, PUT і PATCH неіснуючого id — кожен перевіряє статус і тіло).

<a id="BUG-API-7"></a>

### BUG-API-7. Фільтр за датою заїзду не знаходить бронювання з заїздом саме в цю дату
- **Серйозність:** normal — пошук «від дати» пропускає бронювання на першу ж дату.
- **Середовище:** https://restful-booker.herokuapp.com, 25.11.2026.
- **Кроки:** 1) створити бронювання з `"checkin":"2027-01-10"`; 2) `GET /booking?checkin=2027-01-10`.
- **Очікувано:** Документація `GET /booking`: фільтр повертає бронювання з датою «більшою або рівною» вказаній. Заїзд 10.01 ≥ 10.01 — бронювання є в результаті.
- **Фактично:** бронювання в результаті немає; з `checkin=2027-01-09` — є, тобто фільтр працює як «строго після».
- **Відтворення:**
  ```bash
  curl -s 'https://restful-booker.herokuapp.com/booking?checkin=2027-01-10'   # id бронювання з заїздом 2027-01-10 у списку відсутній
  ```
- **Тест:** BUG-API-7.

<a id="BUG-API-8"></a>

### BUG-API-8. Фільтр за датою виїзду працює навпаки
- **Серйозність:** normal — пошук повертає не ті бронювання, які описано.
- **Середовище:** https://restful-booker.herokuapp.com, 25.11.2026.
- **Кроки:** 1) створити бронювання з `"checkout":"2027-01-15"`; 2) `GET /booking?checkout=2027-01-14`;
  3) `GET /booking?checkout=2027-01-16`.
- **Очікувано:** Документація `GET /booking`: фільтр повертає бронювання з датою «більшою або рівною» вказаній. Виїзд 15.01 ≥ 14.01 — знайдено; 15.01 ≥ 16.01 — ні.
- **Фактично:** навпаки: з `checkout=2027-01-14` бронювання немає, з `checkout=2027-01-16` — є. Фільтр повертає
  бронювання з виїздом **до** вказаної дати (саму дату включно).
- **Відтворення:**
  ```bash
  curl -s 'https://restful-booker.herokuapp.com/booking?checkout=2027-01-16'   # знаходить бронювання з виїздом 2027-01-15
  ```
- **Тест:** BUG-API-8.

<a id="API-NOTE-1"></a>

### API-NOTE-1. DELETE відповідає 201 Created (задокументовано)
`DELETE /booking/{id}` повертає `201 Created`. Документація restful-booker прямо описує саме таку відповідь,
тож це не баг проти специфікації, а відхилення від семантики HTTP (очікувано `200` або `204`): низька
серйозність, питання до власників API. Тест флоу перевіряє `201` як задокументовану поведінку.
